# Sprint 3 — Learning Goal 3: Problem statement and Portflow recovery

## Learning Question

How do I frame my technical work as a human-centered city problem so assessors can see the "why" behind what I build?

## S — Situation

Mats gave me 1/4 on all learning goals in Sprint 2. His feedback: "Choose a human-centered problem from the city and describe what you are going to do to address it." He also said: "Come talk to me ASAP, if you keep going this way that means that you won't pass the semester."

My technical work was solid. The framing was absent. No problem statement. No learning goals written upfront. No weekly expert feedback recorded. All three sprints had code but no story.

## T — Task

Write a human-centered problem statement. Restructure all Portflow evidence to connect the technical work to the city problem. Set up a feedback workflow.

### Deliverables

**Analysis document** — [Analysis - Parking search traffic problem framing](Analysis%20-%20Parking%20search%20traffic%20problem%20framing.md)

What city problem my parking tile addresses and what was missing in my earlier evidence.

**Advise document** — [Advise - Expert feedback workflow](Advise%20-%20Expert%20feedback%20workflow.md)

How I should collect and record feedback going forward.

## A — Action

I researched parking search traffic statistics (Shoup 2017: up to 30% of inner-city traffic in busy areas). I wrote `problemStatement.md` connecting the parking system to Amsterdam's 2030 emission-free goal. Committed as `dbb1bc8` on May 4. Documented in the [Analysis](Analysis%20-%20Parking%20search%20traffic%20problem%20framing.md).

I then mapped what I was doing (verbal feedback, not recorded) vs what assessors see (zero feedback in Portflow). I created a concrete weekly plan. Documented in the [Advise](Advise%20-%20Expert%20feedback%20workflow.md).

## R — Result

The [Analysis](Analysis%20-%20Parking%20search%20traffic%20problem%20framing.md) showed the problem is real and my technical work fits it. But I had never written it down until Mats forced the issue.

The [Advise](Advise%20-%20Expert%20feedback%20workflow.md) produced a weekly feedback plan: ask, record, respond. The main gap was not technical but a habit of working silently.

## R — Reflection

This was the most important learning goal of Sprint 3. Not because the code was hard, but because I learned that assessors do not grade what you built. They grade what you show. Mats and Gerald both said the same thing in different words. Building without framing is invisible work.

I should have written the problem statement in Sprint 1.

## T — Transfer

Sprint 4: write learning goals in week 1. Ask Gerald for feedback in week 1. Record everything in Portflow. If it is not recorded, it did not happen.
